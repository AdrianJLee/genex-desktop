# Building this Unity game in its editor

This game is built in the user's open Unity editor through unity-editor__list_commands, unity-editor__describe_command and unity-editor__run_command (Unity's Pipeline package, com.unity.pipeline). list_commands names every command the open editor offers, what each does and its tags; describe_command lists one command's parameters; run_command runs it with those parameters. Read a command's parameters before you first run it: a wrong or missing one fails with the editor's own words for what it wants. Calls go to this game's own Unity project (the folder holding ProjectSettings/, in the game's folder) and only while it is open in Unity with the Pipeline package. When a call says the project is not open, call unity__open-editor; when it says the project has no Pipeline package, call unity__setup (the user confirms it); when Unity is busy or still starting, call again in a moment; when it says Unity's main thread ran nothing, wait a minute and call again, and only if that keeps happening call unity__restart-editor (the user confirms it; Genex saves first while Unity still answers, else unsaved editor work is lost). To close Unity, call unity__quit-editor: it saves first; open it again with unity__open-editor. Anything else a call says to do, tell the user instead of retrying.

Scripts are C# files under Assets/: write and edit them as files. After a script changes, call recompile and read recompile_status until it is idle: its errors are the compile errors to fix, and while Unity reloads its scripts its commands wait or answer that it is busy, which is not a failure. A new script's type exists only after that recompile. Keep every .meta file beside its asset: Unity writes them, and they hold the ids scenes and prefabs point at, so never write one by hand, and move, rename or delete an asset with the editor's asset commands, which carry the .meta along. Scenes (.unity) and prefabs are files Unity owns: change them with editor commands, not by editing their text. Library/, Temp/, Logs/, obj/ and UserSettings/ are Unity's scratch: never edit them.

Build the game into its scenes, not at runtime: the level, its lights and its camera belong in the saved scene, where the user sees and edits them in Unity and where Genex's save points and reviewer see them, since their pictures are the main camera's view of the saved scene outside Play mode (a scene that builds itself only when Play starts gives them an empty frame). Keep the main camera where the player first sees the game. Build with code, not one command at a time: for a level, a layout or anything with many objects, write a C# file with a static method under Assets/Editor/ (it uses UnityEditor and UnityEngine as an editor script does) and run it with run_command run_script {file, entry}, which compiles that file and runs the method at once, with no recompile; keep the file, so the scene can be built again, make the method replace what it made before, then save the scene. Meshes, textures and materials such a script makes in code are saved as assets first (AssetDatabase.CreateAsset under Assets/), or the saved scene loses them. When such a script makes an asset again from a new source (a new model's meshes, say), save it under a new name and point what uses it there: copying new data over an asset Unity already loaded (EditorUtility.CopySerialized) can leave the open editor drawing the old one until Unity restarts. When a picture of the game disagrees with what the files say, the picture is what the player sees: find out why before you say the work is done. Make at runtime only what appears during play, such as spawned pucks, projectiles and effects. batch runs several commands as one undo step.

Every change lands in the user's editor at once. Many commands that change or delete something want confirm: true, and take dry_run: true to show what they would do first. Stop Play mode (editor_stop) before you edit a scene, since changes made during play are lost when it stops. Save before you say the work is done, with save_scene and the scene's path, or save_all: only saved files are in the game's checkpoints. A scene that has no file yet must get one with save_scene and a path under Assets/ first: Unity would otherwise ask for its name in a dialog that stops the editor, so the connector refuses such a save. Never run anything that makes Unity show a dialog nobody is there to answer. To see the game, call capture_game_view: the picture comes back as an image you can look at. It needs an open Game view window, or source: "camera" to render a camera; pass save_path only to keep the file (it lands under Assets/). The game keeps running while Unity is behind other windows. Read the editor's log with console.

You may do in the editor what a person does there. Add a package the game needs yourself, such as the High Definition Render Pipeline (com.unity.render-pipelines.high-definition) or the Input System (com.unity.inputsystem): package_search finds it, package_add takes a registry name, a repository's URL, or file: and a folder inside this game, and you read package_status until it is done; scripts reload afterwards. Switch the build target with switch_build_target, and build a player with build, naming outputPath under Builds/ in the Unity project (confirm: true; read build_status until it is completed). Frame rates measured in Play mode inside the editor include the editor's own work: say which you measured. Run a menu item with menu and its path, but prefer a command, since a menu item that opens a dialog stops the editor until someone answers it. Not available to agents, alone or inside a batch: running C# text that is in no file (eval, eval_file), quitting Unity (call unity__quit-editor) or opening another project in it, and Pipeline's authoring root and runtime settings. A file a command names must be inside this game's folder; paths are relative to the Unity project (Assets/…).
